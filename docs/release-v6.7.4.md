# Proxy Checker v6.7.4 — 把测速状态从「引擎实例」提到「进程」

## 背景

v6.7.3 上线后第二轮独立审核又指出五条，逐条核实**全部成立**。其中 P1 那条比我预期严重：
基线测量被移到批次开始前之后，它跑在**维护批次的 120 秒预算之内**，而基线状态挂在**引擎实例**上——
`apply_runtime_settings` 每保存一次设置就重建引擎，于是每个新引擎都会重新测一次基线（最坏 66 秒），
外部表现就是「持续维护一直没进展」。

四条缺陷其实同一个根因：**运行期状态挂在引擎实例上，而非进程级；基线成本没有上界**。本版一次性解决。

## 修复清单

### ① 基线测量吃掉维护批次预算（P1）
- 基线状态提到**模块级**：`attempted / value / readings` 全进程共享，**每进程最多尝试一次**（成功、失败、超时都算尝试过），
  重建引擎不再重测。
- 新增 `warm_uplink_baseline_async()` 公开入口，供 server.py 在**进程启动**与**引擎重建后**用后台线程预热（不在批次内）。
- 新增 `UPLINK_BASELINE_TOTAL_SECONDS`（默认 10 秒）**总超时**：超时就用已有读数（够稳才用），否则放弃截断——
  宁可不截断，也不占着批次预算。
- 单元断言：两个引擎实例共享基线状态，第二个实例 **0 次直连测量**。

### ② 基线测量期间停止请求不能及时生效（P2）
整个基线测量包在总超时里，且**轮间与块间**都检查停止信号；批次开始前若已置停止信号则不测。

### ③ 基线测量不占测速配额（P2）
基线同样是上行流量：与别的工作区在跑的探针叠加会到 3 条并发；更糟的是**争用下基线会被低估**，
截断值随之偏低——那正是「错截快线」的入口（比留一个假高值更危险）。
现在基线测量也走同一把进程级配额，**拿不到就本次不截断**，不阻塞、不重试。

### ④ 配额仍是「每引擎实例一份」（P2）
`_uplink_gate_sync` 挂在实例上，保存设置重建引擎会多出一份配额，多工作区并行时会各自放大。
改成模块级单例（`_UPLINK_GATE` + 模块级锁），真正进程级。
单元断言：两个引擎实例拿到的是**同一个**闸对象，合计在飞 ≤ 上限。

### ⑤ 保存后本地与云端读数不一致（P2）
`saveRepoRequest` 成功后用**客户端提交的那份**回写本地缓存，而服务端保护下来的 `up_kbps`/`up_error` 不在响应里
⇒ 仓库列表看不到读数，直到刷新页面。
改成保存成功后**后台回读云端仓库**并刷新本地缓存：带 `repoCacheGeneration` 守卫（保存期间用户又改了东西就放弃回写），
回写不再触发二次同步；网络/解析失败静默放弃。

## 保持不变

- 探测方法、基线截断语义（只降不升、不稳定则不截断）、门禁语义（只对测到读数的轮次卡门槛）、
  `?up_min=` 导出语义全部不变。
- 其余五个档位行为逐字不变；不带参数的订阅导出逐字不变。
- 不自动部署、不重启服务、不改用户配置。

## 验证

- 先红后绿：① 用「两个引擎实例」复现基线重测（旧实现第二个实例仍会直连测量）；
  ④ 用「两个引擎实例」复现配额放大（旧实现拿到两个不同闸）；⑤ 用真实 server 复现「保存后本地缓存缺读数」。
- 修后同一批用例转绿，并新增：基线总超时（卡住直连 → 10 秒内返回且不截断）、失败不重试、基线抢配额、
  停止信号及时生效、前端回读与 generation 守卫。
- 既有 18 个本地测试脚本与 Docker fixed/isolated 门禁继续全绿。

## 升级

- 版本镜像：`ghcr.io/fujunchao/proxy-checker:v6.7.4`，发布同时更新 `latest`，支持 linux/amd64 与 linux/arm64。
- 本次只发布、不部署。升级后无需改配置；进程启动时会有一次约 2 秒的基线预热（后台线程，不阻塞启动）。
- 回滚：`UPLINK_PROBE=0` 关闭整个上行维度；`UPLINK_BASELINE_KBPS=-1` 只关截断；
  `UPLINK_BASELINE_TOTAL_SECONDS=0` 取消基线总超时（不建议）。

具体范围见 [v6.7.0 实施方案](implementation-plan-v6.7.0.md) 与 [v6.7.3 发布说明](release-v6.7.3.md)。
