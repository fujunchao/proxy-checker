# v6.6.4：发现公平性与累计观测

## 问题证据

2026-10-14 用户提供的运行日志中，约六小时执行 224 个复测批次、70 个发现批次；74 个复测批次只有 1～2 条。发现仍有入库，但来源游标仅推进两次，第一源到第二源相隔近六小时。原始日志和身份信息不进入仓库。

## 实施方案

1. 用按来源保存的候选队列替代单一来源队列，每个来源小批次结束即轮转。保留独立未完成重试队列，来源和重试交替；旧游标和在途输入迁移，不清空库存或已检测历史。
2. 保留 `refresh_share` 连续批次数上限，增加默认 120 秒的连续复测耗时预算；零散到期项最多连续占一个复测批次。发现批次重置预算；没有到期库存时继续发现。
3. 每源最多 50000 候选，来源队列合计最多 100000，重试队列最多 50000；超额来源不截取头部、不覆盖已接纳候选，轮转其他来源后重试并显式报告。来源空队列重新抓取设冷却，避免空源高速请求。
4. 在权威快照内记录升级后累计拉取、读取候选、已提交检测以及新增／更新／移除；仓库变化的计数与观测收据原子提交。页面区分本批与累计，并标明 22/33 的来源覆盖范围，不冒充历史全量统计。
5. 维持单工作区单批次、进程网络配额、档位门槛、skip/force、取消／人工编辑栅栏及订阅兼容。此次不接入另外 11 个非纯文本源，不提高检测并发，不自动部署。

## 验收与发布

- 真实协调器回归：大来源让出下一来源、旧队列迁移／重启、慢项重试、零散到期、公平时间预算、来源失败及队列容量、累计计数的重试幂等。
- 前端用真实 DOM 验证累计统计及当前批次互不混淆。
- 先运行新失败回归，再完成修复；保留所有已有测试和 Docker fixed/isolated 冒烟门禁。
- 工作分支完整 CI 通过后快进 main；main 同 SHA 验证通过后发布 `v6.6.4`。标签工作流再次测试并构建 amd64/arm64 镜像，核验镜像和 Release 后报告完成。
