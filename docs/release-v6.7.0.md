# Proxy Checker v6.7.0 — 上行吞吐维度与 up_min 订阅过滤

## 改进

- Z.AI / ZCode 档新增**上行吞吐**读数 `up_kbps`（KB/s）。它回答的是「324KB 的请求体要多久才能写进这条线路」，与既有 `latency`（几 KB 下行的往返时间）是两个维度：实测下游首字延迟与 `up_kbps` 的相关系数为 0.975，与 `latency` 基本无关。一条 RTT 40ms、上行 8KB/s 的线路在旧评分里是优等生，但对下游毫无价值。
- 测速用**独立端点**（`https://speed.cloudflare.com/__up`），刻意不碰 `zcode.z.ai`：后者的 443 是 TLS 端口，收到非 TLS 字节会在 10ms 内回 400 并重置连接，量到的是「内核缓冲容量 ÷ 对端关闭时间」，方向都不确定。
- 采样按方案硬约束做：最多写 2MiB，**只统计跳过前 128KB 之后的稳态区间**。前 ~128KB 会瞬间进内核缓冲（0.2–0.3s），512KB 载荷会被完全掩盖（实测差 6.8×）。里程碑采样让慢线也能在预算内出读数——12KB/s 的线在 40s 内发不满 2MiB 也照样有稳态读数，这是「4MiB 整体计时」做不到的。
- 成本可控：**每线路只测首轮**（后续轮复用读数）、进程内 **6 小时**复测节流、只有**服务已可达**的线路才测速。每线最多消耗 2MiB 上行、单次最多 40 秒，并有慢线提前收尾。
- 新增独立**上行门禁**：与 `required_probes` 分开——后者回答「摸不摸得到目标」，上行门禁回答「够不够快」。语义刻意是「**测不到 ≠ 不达标**」：全部轮次都没拿到读数（端点被墙、库版本不支持、整体超时）时放行，只要任何一轮测到读数，就必须每轮都 ≥ 门槛（默认 85KB/s）。这是为了避免测速基础设施故障把整仓线路判成无效。
- 新增订阅过滤参数 `?up_min=85`：只导出实测上行 ≥85KB/s 的线路；缺读数的旧条目视为不达标（「没测过」不能当「快」）。过滤排在 `limit` **之前**，带 `limit` 的链接先缩小集合再截断。
- `up_kbps` / `up_error` 随检测结果、仓库条目与订阅 JSON 输出，下游可以据此排序；带 `comment=1` 的 TXT 元信息也会带 `up_kbps`。
- 仓库写库时，如果本轮没测到读数，**沿用历史读数**（`up_error` 照写）。否则测速端点一次抖动就会把整仓读数抹掉，让 `?up_min` 订阅瞬间变空；真实降速仍会被新读数覆盖并过滤掉。
- `config.json` 支持 `uplink_probe` / `uplink_min_kbps` / `uplink_budget` / `uplink_min_bytes`（可选，有默认值），`.env` 支持 `UPLINK_PROBE` / `UPLINK_MIN_KBPS`；`docker-compose.yml` 已透传这两个环境变量，容器部署下回滚开关同样生效。
- 并发闸 `UPLINK_PROBE_CONCURRENCY`（默认 2）/ `UPLINK_PROBE_WAIT_SECONDS`（默认 3 秒）：同一事件循环内最多 2 条线路同时测速，拿不到名额就**跳过**而不是排队等。这一项防的不是流量成本，而是**宿主上行争用**：30 路并发检测时如果每条都同时发 2MiB，部署机上行会被摊薄（例如 2570KB/s ÷ 30 ≈ 85KB/s，正好卡在门槛线上），快线会被系统性读成临界线。跳过只损失这一轮读数，不会拖住整个维护批次。

## 保持不变

- 其余五个档位（generic / openai / grok / gemini / claude）**行为逐字不变**：`uplink_probe` 默认 False，且 summary 里的上行明细只在该档启用测速时出现，`gates` 里不会多出 `uplink` 键。
- 不改 latency 判据、不改 grade 分级、不动 `required_probes` 的既有语义，不改变仓库入库策略与公共订阅格式。
- 不带任何参数时 `/api/repo/<token>.txt` 与从前的输出逐字一致，老订阅链接不受影响。
- 检测轮数、并发上限、请求超时、协议识别超时不变；硬超时上限从 120 秒提到 180 秒，仅用于容纳单次测速预算（每线路只发生一次）。
- 不自动部署、不重启服务、不修改用户配置。

## 验证

- 先复现再修：先在 curl_cffi 0.16.3 上验证「`response.upload()` 不存在」与「`content=<async generator>` 可用」，据此确定里程碑实现形态，再实现功能。
- 方向与量级用**已知真值**校验：本地令牌桶限速 CONNECT 代理（200KB/s）下读数落在 [0.5×, 3×]，同一条线在 60KB/s + 8s 预算下仍能出读数并标 `truncated=True`。
- 实机对账（部署机容器内，只读线上仓库快照、不写 `/data`、不重启服务）：用新 `proxy_check.py` 对线上仓库 142 条 Z.AI 线路跑一轮（并发 8、单轮），再用系统 `curl -w speed_upload`（libcurl，与 curl_cffi 是两套栈）串行抽测 12 条横跨量程的线路。结果见下方「实机对账结果」。
- 导出链路端到端：本地起真实服务加载仓库快照，验证 `?up_min=85` 的条数显著少于全量、`?up_min=85&limit=N` 先过滤后截断、无参数导出逐字不变。
- 既有 15 个测试脚本（含真实容器冒烟、前端真实 DOM、维护管线协调器）与 Docker fixed/isolated 门禁全部保留；新增 `tools/test_uplink.py`（100 条断言）并接入 CI。
- 发布只在工作分支、main 和标签对应 SHA 的完整 GitHub Actions 验证通过后完成，并核验双架构镜像与 `latest`。

## 升级

- 版本镜像：`ghcr.io/fujunchao/proxy-checker:v6.7.0`，发布同时更新 `latest`，支持 linux/amd64 与 linux/arm64。
- 本次只发布，不自动部署、不重启服务、不修改用户配置。升级后第一轮 Z.AI 巡检开始写入 `up_kbps`。
- **老仓库在首轮巡检写入读数之前，带 `?up_min` 的订阅链接会是空的**（旧条目没有读数，按语义视为不达标）。建议等一轮 Z.AI 巡检完成后再把订阅链接换成带 `up_min` 的形式；也可以先按方案 §8 建议用 `up_min=50` 观察一周再收紧到 85。
- 下游订阅链接推荐写成：`https://<checker-host>:8888/api/repo/<token>.txt?usable=1&up_min=85&stable=1`。
- 回滚：设 `UPLINK_PROBE=0` 并重启（compose 部署已透传该变量）。回滚后 zai 档退回「只看可达性」，既有档位行为逐字不变。
- 全量巡检会多花上行流量：每线路最多 2MiB，且只有服务可达的线路才测。若带宽紧张，可只开 `UPLINK_MIN_KBPS` 过滤而不订阅 `up_min`。

## 实机对账结果（2026-11-07，部署机 154.12.85.101）

用线上仓库快照里的 142 条 Z.AI 线路跑一轮（并发 8、单轮、容器内执行，不写 `/data`、不重启服务）：

- 142 条里 **74 条测到读数**，其余是服务/握手失败（SOCKS 握手 15、SSL/TLS 5、CONNECT 502 2、连接重置 2）或触顶预算 8 条——这些本来就不该进仓库。
- 读数分布（KB/s）：最小 12、P10 37、**中位 818**、P90 1942、最大 7142；其中 **62/74 ≥ 85KB/s**。仓库里这批线路是 `stable_only` 反复筛过的，比方案里「线路池中位 22KB/s」的原始池子明显更好。
- **`latency` 与 `up_kbps` 的相关系数 r = -0.098**（仓库里的旧 `latency` 与 `up_kbps` 是 -0.166）：在本机这批线路上，两者几乎不相关——这正是方案 §0 的前提，也说明旧评分体系确实量不到这个维度。
- 与 `curl` 独立对账（12 条抽样里 8 条两边都拿到有效读数）：点值比值中位 **2.05×**，4/8 落在 0.5–2×；**85KB/s 的门槛判定 8/8 一致**；Spearman 秩相关 0.714。两条线路的读数差到 8–11 倍（缓冲吸收与瞬时抖动叠加），**因此本版不承诺「与独立实测差异 <2×」**，只承诺门槛判定可用。
- 有 4 条线路 `curl` 在 40 秒内根本传不完 2MiB（必然超时），而里程碑版照样给出了读数——这正是弃用「4MiB 整体计时」退化版的原因。
- 导出链路端到端（本地起真实 `server.py` + 注入上述真实读数的仓库快照）：无参数 144 行不变；`?up_min=85` → 62 行；`?up_min=85&usable=1&stable=1` → 50 行；`?up_min=50` → 63、`?up_min=200` → 55（单调）；`?up_min=85&limit=5` → 5；`?up_min=85` 的 JSON 每条读数都 ≥85；`comment=1` 元信息含 `up_kbps`。

**已知限制**（下一版再改）：点值精度受「前 1–2MB 被内核缓冲吸收」影响，快线之间拉不开差距（读数在 ~700KB/s–7MB/s 之间抖动）；若要把点值噪声压到 2× 以内，需要更大载荷或改成「用末尾窗口估算」的稳健估计量，代价是流量成倍。**因此门槛建议按方案 §8 先用 `up_min=50` 观察一周，再收紧到 85。**

具体范围见 [实施方案](implementation-plan-v6.7.0.md)。真实首字延迟收益需要下游按 `up_kbps` 改派之后才能对照观测，不以合成测试冒充线上实测。
