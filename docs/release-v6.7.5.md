# Proxy Checker v6.7.5 — 仓库回读交错与基线停止修复

本版修复 v6.7.4 复核中剩余的三个问题：仓库回读与保存交错导致本地版本落后、API 首次检测的基线传输无法及时停止，以及基线总超时配置未传入 Compose 容器。

## 修复内容

### 仓库保存与回读保持正确顺序

旧流程中，保存 1 返回版本 2 后发起后台回读；保存 2 已发出但响应未到时，回读会增加缓存代次，导致保存 2 返回的版本 3 被忽略。下一次新增代理仍携带版本 2，发生冲突后被云端刷新覆盖。

现在每次保存开始都会推进请求序号，旧保存发起的回读随即失效。回读需要同时满足请求序号、编辑代次和工作区身份校验；新的保存响应可以正常推进版本，仍会回读服务端保护的测速字段。回读失败时保留当前缓存。

### 基线传输可以响应停止

API 首次检测可能自己执行基线测量。静默连接没有上传块或响应，原有轮间、块间检查无法察觉停止请求。

现在基线传输作为独立任务运行，等待期间每 50 毫秒检查停止信号，并同时受单轮与剩余总预算限制。停止、超时和外层任务取消都会清理传输，再归还测速配额；不发布未完成的检测结果。进程级基线仍只尝试一次。

### Compose 透传基线总超时

`docker-compose.yml` 与 `.env.example` 补齐 `UPLINK_BASELINE_TOTAL_SECONDS`，默认 10 秒，`0` 表示不设总上限。部署时修改同目录 `.env` 即可传入容器。

## 验证

- 新增回归在修复前分别复现：本地版本 `2 != 3`、停止后阻塞传输仍未取消，以及 Compose 缺少配置映射。
- 前端回归覆盖旧回读先于或晚于下一笔保存响应、正确版本继续提交新增代理、在途编辑与身份切换保护。
- 后端回归通过真实检测主循环验证静默基线传输的停止和外层取消，检查未发布结果、基线完成通知以及配额归还。
- 总超时用例确保确实进入阻塞传输并取消，避免过短预算导致测试未触及传输路径。
- 持续集成使用 Compose 实际解析配置，核对 `0` 与非默认值 `7` 的透传。
