# 持续维护：试运行交付说明

日期：2026-10-14（北京时间）。本次仅交付代码，不打版本标签、不推镜像、不部署，不改变正在运行的任务。

## 实际基线与范围

- 基于 `268a571`（v6.6.2），原有摘要优先、游标分页、IndexedDB 缓存和列表局部更新全部保留。
- 新模式实现存量优先复测、发现游标分批、数量／独立时间节拍发布、取消栅栏与完整快照。
- 老配置默认 `maintenance_mode: "legacy"`，不自动启用，不把 `skip` 改成 `force`。旧模式仍整轮结束后发布，但使用统一版本提交和有限网络租约。
- 不修改 zcode2api-plus；订阅路径、token 归属、JSON 数组顶层、毫秒时间戳、TXT 格式、过滤参数及既有档位门槛不变。
- 原有 CI 默认 shell 的 `tee` 会吞掉测试退出码；本分支显式指定 `bash`，开启 `pipefail`。此前的绿灯不能替代修复后全门禁证据。

## 显式启用

网页“自动任务”中选择“持续维护（推荐）”，确认**自动任务目标档位**、发现的 `skip/force` 和入库策略，然后勾选原有的“启用后台自动检测”并保存。没有新增第二个自动开关。

“立即运行”只执行一个有限批次；持续接续需要原有 enabled 开关开启。旧日程只对 legacy 模式生效。关闭页面不影响后台调度。

管理请求 `/api/auto/save` 中的 `config` 示例（正常登录后使用原有工作区身份）：

```json
{
  "enabled": true,
  "maintenance_mode": "continuous",
  "target_profile": "zai",
  "detect_mode": "skip",
  "repo_update_policy": "stable_only",
  "refresh_seconds": 900,
  "refresh_batch": 100,
  "discover_batch": 200,
  "batch_seconds": 120,
  "publish_count": 20,
  "publish_seconds": 10,
  "refresh_share": 4
}
```

这只是选择 zai 档位的例子；generic 和其他档位保持原语义。轮数和工作区并发仍来自已有全局设置。页面保存保留这些高级参数，不会覆盖成默认值。

## 排程、限额及可观测性

- 每工作区一个协调器，每次只跑一批，批间重新读取配置和当前仓库。最多连续 4 个 refresh 批次后让出一个 discover 批次。
- 仅刷新当前档位已发布项。缺少档位的旧项、其他档位的项单独计数，不自动迁移或删除。首版不提供批量档位迁移向导；需要用户明确整理后再维护。
- 用实际 `last_checked_at` 选到期项；未知时间优先尝试。不使用 `added/updated` 冒充复测时间。未完成项短期让出队首，最多等待 60 秒后重新进入选择范围。
- 首版新模式轮转已有 `parser=plain` 的纯文本来源。每次一个源，读取期限 20 秒、单次 socket 等待 5 秒、最多 4 MiB／50000 个候选。超过限额显式报来源错误，不永久截断为头部。旧“全部来源”集合保持不变。
- 候选游标和在途输入持久化。已消费前缀回收，未完成输入回到队尾；重启恢复输入，不恢复内存观测。去重、已检测跳过和现有仓库键过滤在每个发现批次执行。
- `PROCESS_NETWORK_LIMIT` 是进程启动时读取的检测客户端配额，默认沿用 `MAX_CONCURRENT_LIMIT`（默认 200），范围 1–1000。refresh/discover/手动检测共享 FIFO 租约；同工作区最多一个租约。它是客户端配额，不是操作系统所有 TCP 连接的计数。原有可选浏览器深检也需等待租约。
- 检测器继续使用有限工作者及原单代理硬超时；旧模式和手动输入按 100 条归还／重获租约，不占用全量来源直到结束。
- 新模式每批最多保留 200 条完整原始结果；页面每分类最多保留 1000 条诊断。分页只描述当前 run，不承诺网页能回放离线期间的每一个批次。最后一批保留 15 分钟，进程最多保留 64 个工作区尾页；过期明确返回 410。
- 每批待发布队列容量是数量阈值的 2 倍；另有最多“工作者数”的正在交付观测及一个发布批次。预算中断会提交这些完整观测，人工取消则丢弃未提交部分。
- 仓库最多 100000 项／64 MiB 权威快照；每工作区最多 8 个在途发布记录，每个 run 最多 100000 观测收据。完成 run 删除收据，迟到 run 不在活动表中即拒绝，重启 boot 标识不匹配也拒绝。容量不足停止新增，不清掉仍有效的保护记录。
- 已检测历史达到 200000 项时停止新增并提示；不偷偷淘汰历史改变 skip 语义。最多 16 个并行维护工作区、32 个保留的手动任务；手动单次输入最多 50000。到期工作区按最近执行时间排序，避免前几个工作区长期占用启动名额。
- 状态展示到期数、最老**已知**复测年龄、时间未知数、发现积压、未完成数、待发布、实际仓库版本／数量和提交新增／更新／移除／冲突数。15 分钟是调度目标，不是 SLA；结果通过不等于提交成功。
- 日志实际输出脱敏工作区哈希、run、批次类型、进度和发布版本。HTTP 访问日志不输出订阅 token、URL 或查询参数；来源异常只保留异常类别。

## 提交、取消与时间语义

`repository.py` 是唯一持久化接缝。手工 merge/replace、旧兼容入口和自动发布均经过它。每个工作区串行提交，检测网络 I/O 在锁外。

- 自动观测包含 run、启动标识、配置代次、规范化端点（协议及凭据大小写不被折叠）、档位、观测 ID、开始／完成时间及读取版本。
- 提交重新读取当前仓库，只修改该观测允许修改的端点；同端点旧版本不覆盖新结果，同 run 重试不重复计数。
- 人工保存使用真实 `base_revision`，不能靠 `base_count` 判断同数量变更。新网页从 `X-Repo-Revision` 读取版本，提交时携带。旧管理客户端不带版本时只能追加新键；replace 非空库或同键覆盖需要刷新并升级管理页面。**公共订阅消费者不需要升级。**
- 人工修改采用保守的**整个工作区 epoch 栅栏**：人工编辑时同批其他在途观测也会冲突跳过，下批重新检测。这不是永久删除名单，后续新发现仍可再次发现该地址。
- 修改自动配置／关闭／停止先使在途提交失效。已提交批次保留；未提交不再发布。连续模式“停止”会暂停接续，需再次保存或立即运行；仅改配置的取消会在终态后使用新配置接续。
- 未完成轮次不发布、不记为线路失败。单代理原硬超时仍属于完整失败；批次预算、配置取消、服务退出属于任务级未完成。
- `last_ok` 和新增 `last_checked_at` 使用完整检测完成时刻（毫秒）；`updated` 沿用结果更新语义，使用该观测完成时刻。`last_published_at` 是管理元信息，独立表示实际提交时间。UI 保存不能递增成功次数、刷新检测时间或抹掉既有检测计数。

## 文件布局、迁移与异常恢复

升级后 `<token>.snapshot.json` 是单一权威快照，包含 JSON 正文、TXT 正文、条目版本、观测收据、维护游标及校验和。先完整序列化／校验，写固定 `.tmp` 文件并 fsync，再原子替换；Linux 另 fsync 目录。写入失败提供旧完整快照；替换后失败则提供新完整快照。幂等信息与仓库不能分离。

读取请求固定在一个完整快照；JSON、TXT 返回该快照的版本头。两个顺序请求跨版本是正常现象。只保留一个权威文件和最多一个临时文件，不堆积历史代次。

旧目录无快照时严格读取旧文件；不会把坏 JSON 或维护状态当空仓库。若旧 JSON/TXT 地址列表已经不一致，暂停导入，由用户明确选择正确版本。TXT-only 旧目录在首次数据修改前仍保持公共 JSON 空数组的兼容行为，但内部可以选取 TXT 库存。首次维护状态提交保留旧无参数导出正文；首次数据修改后生成兼容格式。旧 JSON/TXT 文件不会双写，也不会在升级后继续充当权威数据。

快照或维护文件损坏时返回明确错误并暂停该工作区写入；不会阻塞其他工作区。恢复需要检查并使用用户备份，不提供“自动清空损坏状态”。部署假定**单个 Python 服务进程**管理一个数据卷；不支持多个实例共享同一卷并写。

## 用户另行授权后的受控升级

1. 记录目前五万条任务进度。本分支没有停止它。旧模式的大任务仍在内存持有未发布结果，直接重启会丢弃那些未提交结果；应由用户选择等待自然完成，或明确停止并接受未提交结果被丢弃。
2. 用户在服务器备份数据卷和配置。不要用开发机真实运行目录演练。
3. 使用最终 SHA 完整 CI 通过的代码，在有限库存和小批次环境先试运行。没有发布镜像，本次不提供已经上线的镜像标签。
4. 显式选择持续维护及正确档位，观察多个 refresh 批次、至少一次发现循环和一次重启恢复。
5. 记录完成→发布延迟、存量最老年龄／积压、增改删冲突、CPU／内存／连接数／请求耗时；再对齐网关收到及复检通过数量。探针通过率不是 405 改善证据。

## 回退至旧版本

先关闭新模式并等待当前任务终态；保留已经提交的仓库。旧版本不认识权威快照，**不能仅降级容器就认为读到了最新仓库**。

用户在服务器对当前完整快照执行只读导出（示例身份是占位值）：

```sh
python tools/export_legacy_repo.py \
  --snapshot /data/repo_data/user_example.snapshot.json \
  --output /backup/prx-legacy-export-new
```

输出目录必须不存在，包含一对旧版 JSON/TXT 和版本／校验和清单。工具不修改源运行目录，中途失败只留下 staging 目录。用户检查结果并备份后，在服务停止的情况下，将这对文件复制到**另一个旧版数据卷**的 `repo_data`；再启动旧版。不要把历史全量快照自动覆盖到现有数据卷，也不要让新旧实例共同写同一卷。

若要恢复本分支，可保留原快照数据卷；如旧版本期间发生人工变更，必须明确选择以旧版当前导出重新导入新的空目标卷，不能悄悄切回过期快照。

## 验证边界

自动化只在 GitHub Actions Ubuntu 使用临时目录、文档保留地址、受控时钟、模拟来源／检测器和本地 HTTP 服务。保留原仓库策略、Z.AI、前端性能、身份、完整冒烟和 fixed/isolated 容器门禁。

真实代理质量、真实部署的内存／网络表现、网关复检收益、平台文件系统的断电行为均尚未在生产验证。故障注入验证文件写入与 rename 各点，不能替代服务器实际断电试验。尚不承诺 405 改善、不自动迁移混合档位、不做新模式非纯文本来源支持。
